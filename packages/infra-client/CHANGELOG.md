# Changelog

What each release of `@fntio/infra-client` changed, newest first. Versions 0.1.0 to 0.1.11 were reconstructed from the commit history on 2026-09-10; from 0.1.12 on, every release adds its entry here before the version bump. Steps a release needs from you are on the wiki's Deploy and Upgrade page.

## 0.6.0 — 2026-10-26

**Upgrade:** hub stacks (`DataStack CredsStack WebStack`), then `NetworkStack` if you run the private network (the device list and delete routes are answered by the device minter). If an admin had set the dashboard layout from the admin Accounts page, put that value in the config (`dashboard: { layout: "sections" | "plain" }`) before deploying: the stored value is no longer read and the deployment runs in `auto` until the block is set.

- Personal access tokens (#52), opt-in with `personalAccessTokens: { enabled: true, maxLifetimeDays? }`: every user creates tokens for scripts, CI jobs, command-line tools and remote development machines on a new **Access tokens** page (user menu) — a name, an optional description, scopes (`api`, `aws`, `network`, `shares`), an expiry up to `maxLifetimeDays` (default 90) and, for `aws`/`api`, an optional subset of their roles. The secret (`icpat_<tokenId>_<secret>`) is shown once; only its SHA-256 is stored, in a new `TokensTable` in `DataStack`. A token acts as its owner with the owner's current access narrowed to its scopes and role subset (decided in `access.ts`); `api` reaches every route the owner could, admin routes only while the owner is an admin; a route outside the scopes answers `403` with `code: "TOKEN_SCOPE"`. Tokens cannot create, list or revoke tokens, and plugin routes refuse them. A disabled or deleted owner's tokens stop working; deleting a user deletes their tokens; revoking takes effect on the next request. New routes `GET /tokens/current`, `GET/POST /tokens`, `DELETE /tokens/{id}`, `GET /tokens/expiry`, `POST /tokens/expiry/seen`, `GET /admin/tokens`, `DELETE /admin/tokens/{id}`; the admin Users page gains an **Access tokens** tab; the bell warns before a token expires and once after. Activity rows written through a token carry `actor.token` (`{ id, name }`). Discovery gains `personalAccessTokens.enabled`.
- Service users carry scopes (#48): an admin picks `aws`, `network`, `shares`, `admin.read.all` or `admin.write.all` when creating one (required on `POST /admin/service-users`) and changes them later with `PUT /admin/service-users/{clientId}/scopes`. The narrow three share the personal-token route table; `admin.read.all` opens the `GET` routes under `/admin` and `admin.write.all` every `/admin` route (it implies the reads). Scopes are read from the registry row on every request, so a change holds from the service user's next call; a route outside them answers `403` with `code: "TOKEN_SCOPE"`. Only the admin scopes make a service user an app admin, for the methods they cover; a service user without them vends the roles granted to it and enrolls machines on the private network (`POST /network/device-key`, `ephemeral: true`) with nothing else, and an `admin.write.all` one manages users and service users like a human admin. **Breaking:** `POST /admin/service-users` requires `scopes`, and every service user is now route-gated. A service user created before this release reads as `aws`, `network`, `shares`, `admin.write.all`, which reaches the `/admin`, vending, device-key and share routes; routes outside that table (`/requests`, `/notifications`, `/preferences`, `/resources`, `/plugins`) answer `403` for every service user, so an integration that used them needs a person's session or a personal access token. The Users page's Service users tab gains scope checkboxes on create, scope badges per row, a **Change scopes** editor and a **Network resources** section on the panel (service users were already valid resource-grant principals through the API). Activity gains `serviceuser.scopes`. The wiki's service-user runbook carries the headless vend-and-join sequence for a VM agent. Personal access tokens are unchanged.
- The tenant / project / stage filter popup beside an Account picker (Request a role, the group and role forms) opens leftwards from its button instead of running off the right edge of the panel (#66).
- Dark mode: the Account picker’s dropdown list (Request a role, the admin forms) sits on the solid popover surface like every other floating panel instead of a translucent overlay the page showed through (#57).
- The dashboard layout is deployment config (#56): a new optional `dashboard: { layout: "auto" | "sections" | "plain" }` block (default `auto`, validated at synth) reaches the API as `DASHBOARD_LAYOUT`; the **Dashboard** select on the admin Accounts page and `GET`/`PUT /admin/dashboard-layout` are gone, and the `__dashboard-layout__` row in the Resources table is no longer read or written. `GET /accounts/home` keeps `layout` and `sectioned`.
- Desktop: a saved deployment that nobody could reach at launch (the app reopening after a reboot before Wi-Fi is back, a power-loss restart) is no longer marked unreachable for good: its tab reads **· waiting for network** and the app re-probes it on its own (every 10 s while offline, then with backoff for about ten minutes once online) before it settles as **· unreachable**; a host that answers but is not an Infra deployment is unreachable at once. Clicking a waiting or unreachable tab retries it (#58).
- Private network: `POST /network/device-key` takes `ephemeral: true` — the device is removed by the control plane 30 minutes after it goes offline instead of being expired after 7 idle days. `GET /network/devices` lists the caller's own devices on every site and `DELETE /network/devices/{siteId}/{name}` removes one (404 for anyone else's); the Network page lists them under **My devices**. `GET /network` gains `devShares: { enabled, maxDurationHours }`.
- Dev shares: a share can be bound to one device (`device` on `POST /network/shares`, the device's name on the site). The port then opens on that device only — resolved by name on every reconciler pass, so a device that re-enrolls under the same name keeps its shares — and always to the owner's own other devices, so a bound share may name no grantees. The one-share-per-port rule applies per device. A `durationHours` above `maxDurationHours` is now clamped to it instead of refused. In the desktop app the share form gains a **Serve from** picker when you have other devices on the site, the share card names the device, and a device's relay leaves shares bound to another device alone.
- Dev shares: `network.devShares.maxActiveSharesPerOwner` (1–200, default 10, checked at synth) sets how many live shares one user may hold — the fixed limit of 10 before; raise it where tools share ports of many machines for one person. `GET /network` reports it next to `maxDurationHours`.
- Threat protection (`loginMethods.threatProtection`): a Medium-risk sign-in — in practice a known user on a new network — is now allowed instead of "MFA if configured". Cognito offers only the password on any attempt it applies MFA to, so for a user without TOTP that action removed passkey and email code without adding a second factor. High risk keeps the step-up and, when `email` is configured, emails the user about the attempt. Upgrade: `CredsStack`.
- Sign-in sends Cognito a device fingerprint (`UserContextData`, AWS's collector vendored into the web app) on every `InitiateAuth` and `RespondToAuthChallenge`, so threat protection scores a known device on a new network lower than a stranger. When a user's usual passkey or email-code sign-in is missing from the chooser because an MFA action limited the attempt to the password, the page says so in one line.
- `GET /accounts`: every role carries `sessionDurationSeconds` (how long its credentials last). `POST /credentials` always returns `expiration`.
- `apiThrottle: { rateLimit?, burstLimit? }` (default 100 rps, burst 200) sets the vending API's stage throttle, which was a fixed 25 rps with a burst of 50 since July. That ceiling applies across every caller — one page load is 10 to 15 calls, so a burst of 50 was three or four people opening the dashboard at once, and the e2e suite tripped it on its own. The per-token WAF rule (`waf.perTokenRateLimit`) is what bounds one leaked token. Upgrade: `CredsStack`.
- Review fixes before release: `DELETE /network/devices/{siteId}/{name}` removes exactly the device listed under that name — a stale duplicate no longer takes the re-enrolled machine (same hostname, suffixed name) with it. `GET /network/devices` answers for the sites that are up when one control plane is down and names the others in `unreachable` (My devices says so). A device-bound share refuses a `hostname` that is not the bound device's. The per-user token cap holds under parallel creates, and `POST /tokens/expiry/seen` counts only the notices it flagged.
- Network page: one block per VPC whatever the number of sites — the bar names the VPC, its account and (with several sites) its site as a chip, and carries that site's Connect / Switch & connect; the **Shares** group and **My devices** follow. Section chips under the header (one per VPC, Shares, My devices, with counts) scroll to each block. Multi-site deployments no longer nest VPCs under a block per network.

## 0.5.0 — 2026-10-16

**Upgrade:** hub stacks (`DataStack CredsStack WebStack`), then `NetworkStack` and every `Connector-<account>` stack if you run the private network — see the wiki's Deploy and Upgrade page, "Upgrading to 0.5.0".

- Bell notices for a change that moves many targets at once are one row, not one per target: when one person gains or loses more than five roles, resources or plugin permissions through a group (a membership or bundle edit) or a cascade, the feed gets a single `kind: BUNDLE` notice carrying `count` and, for a group, `groupId`/`groupName` ("7,346 access grants · group · FullSystemAccess"). Adding a member to a 7,000-role group used to write 7,000 "access granted" rows for them, the pop-up logic re-raised that backlog as a fresh summary every minute, and `POST /notifications/revocations/seen` (one update at a time) could not clear it inside the request timeout. Mark-seen now runs 25 updates at a time; the web app folds raised notice keys older than its 500-key cap into a watermark instead of forgetting them. The activity log's per-person rows under such a change collapse the same way: one `access.gain`/`access.lose` row per person carrying `details.count` ("gained 7346 access grants via group FullSystemAccess") instead of one per target; the primary row's `affected` list is unchanged.
- Renew sign-in before the 12-hour wall, from anywhere: the user menu's "Session ends" row becomes a "Renew sign-in" button that shows the time left (the end time is its tooltip); the desktop tray's session row gains "Renew sign-in…" (desktop app 0.5.0 or later). All of them start a fresh sign-in while the running session, its credentials and the VPN stay up until the new one lands — nothing is torn down mid-task.
- Desktop: closing a backend tab no longer loses its address. The connect screen (the ＋ button) lists every deployment the app has connected to at least once under **Recently connected**, newest first with its project name; click one to reconnect, or its ✕ to forget it after a confirmation. Only that ✕ removes an entry (`recents.json` in the app's data folder, 20 entries). Reconnecting a saved deployment that was unreachable at startup now keeps its login session instead of starting a fresh one.
- **Large catalogs (#39): the portal now holds a 4,000-account, 16,000-role catalog without the pages or the API growing with it.** The catalog (accounts, roles, group names) lives in an in-memory index per API container, rebuilt only when a catalog write moves a version row, and every catalog-sized list — my access, the admin Accounts page, the request picker, the users directory, a group's bundle — serves one paged contract (`?q=&filter[key]=a,b&sort=&limit=&cursor=` → `{items,nextCursor,total,facets}`; without `limit` each route answers its old whole-list shape, so existing clients keep working). Access is still decided in one place before any page is cut; the index lists, it never grants.
- Dashboard (#45): a user who holds an account an admin kept off the dashboard gets a sticky search over everything they hold — results drop down as role rows with the card's actions (star, Console, Get credentials, the desktop auto-login bolt) — above **Signed in now** (roles with running credentials), **Main**, **Favorites** and **Recently vended**, each heading pinned while its cards scroll, and a table of the **Other accounts** (the roles outside Main and Favorites, five to start and more as you scroll; `GET /accounts` gains the `main` and `favorite` facets and a sparse `main: false` on each account for it); everyone else keeps the plain page unchanged.
- Lists in panels and dialogs (a user's or group's roles, a service user's roles, a group editor's picked roles) show five rows, with Show more / Show less and a search box as soon as any are folded away, instead of thirty and "Show more"; the grant-roles dialog is wider and its dimension filter no longer opens off the dialog's edge. New account flag **Show in the Main section** (on by default; `main: false` on `POST/PATCH /admin/accounts`), `GET /accounts/home`, `PUT /preferences/favorites/{account}` (50 favorites, synced across devices), recents from credential and console vends. The admin Accounts page has a deployment-wide **Dashboard layout** choice (`PUT /admin/dashboard-layout`): automatic (the rule above), sections for everyone, or the plain list for everyone.
- Account dimensions (#47), opt-in: `accountDimensions` in the project config stores tenant / project / stage on each account **when it is registered**, read off its name (`<tenant>-<project>-<stage>`; a pipeline may pass `dims` instead), admin-editable on the account form and never re-derived by a rename. They filter the dashboard search, the admin Accounts page, every account picker (request form, role form, grant dialogs) and the group editor, which gains **add one role across many accounts** (`POST /admin/groups/{id}/roles/bulk`, with a dry-run count). The role card's silhouette follows the stage through the config's stage map (`stages`); without the block nothing changes. A deployment turning it on backfills existing rows with `scripts/backfill-dimensions.mjs` (deployment README "Account dimensions"). The dashboard's search and browse results can be grouped by one dimension (a **Group by** choice beside the filter), and registering a role offers the groups that already bundle that role in the account's sibling accounts (same tenant and stage, `GET /admin/groups/suggest`).
- Groups at scale (#43, #44): `POST /admin/groups/{id}/roles` and `DELETE …/roles/{account}/{role}` add or remove one role, written only if absent, so a pipeline registering accounts never races another writer (the full-list `PATCH` is read-modify-write); the add answers with the change (`{groupId, name, role, added}`), not the bundle, and neither call reads the whole bundle — a 4,000-role group answers in well under a second; the access diff behind a bundle edit reads only the touched targets; the group list caps each bundle at 50 roles with `roleCount` and `GET /admin/groups/{id}/roles` pages the rest; **one yearly review per group** (its clock = the latest approval or bundle change) replaces one per bundled role; the users directory caps each user's role and resource lists at 50 with totals, `GET /admin/users/{id}` carries everything.
- Registration is idempotent (#43): `POST /admin/accounts` and `POST /admin/accounts/{a}/roles` answer `200` with the stored row when the same registration is sent again, `409` only when a field differs — a pipeline can retry any step. The admin forms still refuse a duplicate.
- Target-account template (#43): `TargetAccountStack` / `targetAccountTemplate()` synthesize one account-agnostic CloudFormation template (native `AWS::IAM::OIDCProvider`, sub pin through `AWS::AccountId`) for StackSets or Control Tower, so a 4,000-account deployment does not need one CDK stack per account.
- Pickers (#46): every place that listed the whole catalog in a `<select>` or a checkbox wall (request form, add-role form, group form, the grant dialogs on user, group and service-user panels) is a typeahead over one page at a time.
- Access report (#46): `POST /admin/access-report/jobs` builds the CSV in the background (a second Lambda on the API bundle, 15-minute budget, private reports bucket with a 7-day expiry) and `GET …/jobs/{id}` hands back a 15-minute download link; the Users page's export uses it. The inline `GET /admin/access-report` remains.
- Reads bounded by the catalog (#41, #44): `BatchGetItem` retries unprocessed keys and runs in parallel chunks; the admin bell reads the bare directory; the setup checklist counts from the index; the reconciler scans only what it needs.
- Security Hub S3.9 and CloudFront.5: every hub bucket (web app, OIDC issuer, plugin assets) sends S3 server-access logs, and both CloudFront distributions send standard logs, into one new `AccessLogsBucket` in `DataStack` (90-day expiry, kept on teardown when `prod` is on). That bucket is the one that logs nowhere; AWS's own S3.9 text says to suppress its finding. Rides a deploy of all three stacks.
- Private network: the ALB writes its access logs to a bucket of its own in `NetworkStack` (Security Hub ELB.5): SSE-S3, TLS-only, public access blocked, bucket-owner-enforced, objects expire after 90 days, its own access logs go to the hub's shared access-log bucket under `s3/alb-logs/`; the bucket is kept on a `prod` teardown and emptied and deleted otherwise. Rides a `NetworkStack` deploy.
- Private network: ECS.20 passes on every network task definition. The control-server task is three non-root containers with no shared task volume: the init container renders the config and the self-signed TLS pair next to the database on the EFS mount (the access point performs every file operation as uid 0, whatever user the container runs as), the server container serves from there with its Unix socket on a per-container tmpfs and runs the two CLI bootstrap steps itself once the socket answers, so the `bootstrap-user` and `bootstrap-key` sidecars are gone and `Custom::HeadscaleApiKey` reads the key from the `headscale` container's own log stream (`headscale-<site>/headscale/<task>`); the publish-cert step reads the certificate from EFS. The connector task's two containers are non-root too, each with its own tmpfs, and the minted auth key crosses from the aws-cli container to the Tailscale container over the task's localhost instead of a shared file. The control server moves to the upstream `-debug` image tag (same Headscale, plus busybox for the start script). Why the layout changed: a Fargate task volume is root-owned 0755 when the task starts whatever mode the image gives the path, so 0.4.0's non-root containers could only share a volume a root init container had chowned, which kept ECS.20 failing on that container and on the connectors. Rides a `NetworkStack` deploy (each control server restarts once; the EFS directory gains `config.yaml`, `tls.key` and `tls.crt`) and a deploy of every connector stack (each connector re-registers once). Needs Fargate's tmpfs support (platform version `LATEST`, available in all Regions since January 2026) and aws-cdk-lib 2.263 or later.
- Bell: temporary plugin permissions now warn before they end and once more after, like roles and network resources. New routes `GET /plugins/expiry` and `POST /plugins/expiry/seen`; the notice names the plugin and the account.
- Removing an account now also denies its open plugin reviews and deletes a group that bundled nothing but that account's plugin permissions, as the role cascade already did.
- `PUT /admin/plugins/{pluginId}/accounts/{accountNumber}/grants` answers 404 for a user that is neither in the pool nor a registered service user; `DELETE` still takes any id, so a deleted user's row stays revocable. Every plugin answer carries `Cache-Control: no-store`, 204s and errors included.
- The activity log names the plugin on a revoke (it only did on a grant).
- Plugin assets are uploaded with `Cache-Control: max-age=31536000, immutable` (their prefix carries the content hash), matching the app bundle.
- Catalog provider: a construct rename no longer tombstones the record the new resource just wrote (the record remembers the logical id that owns it; CloudFormation's cleanup Delete for the old id is ignored). Provider tests now cover a retried Create, rollback after a failed install and after a failed update, and a reinstall over expired rows.
- CDK tests pin that no method under a plugin path is unauthenticated, that the catalog record depends on the API stage, that no Function URL exists, and the feature's on → empty → off lifecycle.


## 0.4.0 — 2026-10-08

- Desktop: the app updates itself. A packaged app checks the Release feed a minute after launch and every six hours. On macOS the new version downloads in the background; the tray then offers "Update <version> · Restart to install" (the same teardown as Quit, then the new version relaunches), and a plain Quit installs it too. On Windows the installer is still unsigned, so the app only announces the version and the tray row opens the download page. Each Release now carries `latest-mac.yml`, `latest.yml` and `.blockmap` files next to the installers; an installed 0.3.0 needs one last manual DMG, since it predates the updater.
- Private network: three of the four Security Hub findings an ECS or load-balancer control raised against the network stacks pass as shipped, and the fourth narrows. Every control-server and connector container runs on a read-only root filesystem (ECS.5); the Headscale server and its sidecars run as a non-root user (ECS.20), while the connector containers and Headscale's config-writing init container stay root, because a Fargate task volume is root-owned when the task starts whatever the image says, so the first writer of a shared volume must be root (the wiki's Security Posture lists ECS.20 for exactly those); and the load balancer reaches Headscale over HTTPS (ELB.21, ELB.22): the config-writing init container also mints a self-signed certificate at each task start, Headscale serves TLS on 8080 from it, and the target groups and their health checks speak HTTPS (the ALB never validates a target's certificate, so nothing has to be issued or rotated; the key minter and the reconciler reach the admin API over the same HTTPS inside the VPC and verify it against the certificate the task publishes to the SSM parameter `/<resourcePrefix>/headscale-tls-<site>` at every start, which only its own task role may write; the VPC gains an SSM interface endpoint for that read, since the functions have no internet path; removing a site now also means deleting that parameter, next to the API-key secret). Everything a container writes lives on one task volume at `/tmp`, which the init container hands to the non-root uid; the Headscale CLI finds its config from the working directory, so the ECS Exec commands in the runbook are unchanged. Rides a `NetworkStack` deploy (each control server restarts once) and a deploy of every connector stack (each connector re-registers once). The wiki's Security Posture page no longer lists ECS.5, ELB.21 or ELB.22 as accepted.
- API: every `__`-prefixed row in the Resources table is bookkeeping, never a resource. The catalog listing, single-resource reads, the users directory and the network reconciler skipped only the reconciler's own `__reconciler-status__` rows; any other sentinel (a nameless `__catalog-version__` row written by a newer branch's API run against the same tables) reached the name sort and turned `/resources/expiry`, `/notifications/revocations` and `/admin/requests` into 502s.
- Config: `loginMethods.smsOtp` is gone. It never worked (setting it failed at synth: SMS sign-in needs SNS, an origination number and SMS-sandbox exit, none of which the stacks provision). A config that sets it fails type-checking; remove the line. The remaining methods are unchanged.
- Plugin pages: a plugin no longer reloads its data every minute. The portal re-reads plugin discovery on a timer (`plugins.discoveryRefreshSeconds`, default 60) and told the frame `accessChanged` on every answer, so a plugin following the SDK's guidance redrew each time; now the frame hears it only when its account list really changed.
- Fixtures: the sample identities in the web bundle's story and fixture data, the API spec's examples and the desktop tests are invented names on fixture domains. The 0.3.0 release was built from the export before that change, so its bundle still carries a few of the previous placeholder names; no address, key or deployment value was ever included.
- Config: `alertEmail` takes a list of addresses as well as one. Every address gets its own subscription to the ops alert topic (alarms and the issuer canary) and its own confirmation email on the next deploy; the first address is the default `email.dmarcReportEmail`. A single address keeps working unchanged.

## 0.3.0 — 2026-10-07

- **Private network: a resource in another account whose DNS name is also a service name in the hub account got the hub's address.** The reconciler asked the hub's Cloud Map for every resource's name first, so with the hub and a second account each running `litellm.<namespace>.internal` (or any shared label) in VPCs with the same range, the second account's rules pointed at the hub's task and its resource stayed unreachable. Now only a hub-account resource is resolved through the hub's Cloud Map and VPC DNS; every other account's resource goes to its own in-VPC `tailnet-resolver`, and the plain-DNS fallback from the hub is used for it only when the hub has no service by that label. Rides a `NetworkStack` deploy; the affected resources resolve correctly on the next pass.
- Web app and desktop: the end of a sign-in is visible and warned (#29). The profile menu shows "Session ends 6:40 PM"; 15 minutes before it a banner above the page and a pop-up (new "Session ending" kind in the Notifications settings, on by default) say so; the desktop tray lists the time per backend and in its hover text. **Sign in again** from the banner or the pop-up is a handover, not a sign-out: the current session keeps running, credentials and the VPN stay, and the new sign-in takes over with a fresh 12 hours (the old refresh token is revoked). After a forced sign-out the sign-in page says why — the 12-hour limit, a session ended early, or a sign-out in another window — instead of a bare form. `config.json` carries `sessionHours` (the refresh-token validity, from one constant in `WebStack`), so the app never hardcodes 12.

## 0.2.0 — 2026-10-06

- Plugin pages: moving from one plugin page to another now starts that page's own frame. The frame of the previous plugin stayed on screen under a "newer version available" notice until a reload.
- Plugin pages: the frame's colour scheme follows the portal's light/dark choice, so a plugin document themed dark is no longer given an opaque black backdrop; and `applyPluginUi` (`@fntio/infra-client-plugin-ui`) now sets the page base too: see-through background, no body margin, the portal's text colour and typeface, at zero specificity so a plugin's own rules win.
- Private network: a resource's range may be as wide as `/16` (it was `/24`), for a subnet of hosts rather than one database. The reconciler's containment check against approved routes is unchanged, and the form states how many addresses a range wider than `/24` covers.
- Private network: every call the reconciler makes to a site's control server has a time limit (10 seconds; 30 for the policy update), so a control server that accepts the connection and never answers fails its own site for that pass instead of spending the whole pass and leaving the other sites without a policy update; and a catalog row with no address is skipped instead of freezing its site's policy. Both ride a `NetworkStack` deploy.
- **Private network: a DNS name that stops resolving no longer opens the resource's stored range.** The rules hold the addresses the name last resolved to for up to 24 hours after it last resolved, so a resolver blip does not cut access; after that, or for a name that has never resolved, nothing is open and the resource shows "DNS unresolved". Until now the whole registered range opened as the fallback. **Before deploying `NetworkStack`, check the admin Resources page for resources marked "DNS unresolved"**: they work through the range today and will stop until their name resolves (usually a connector stack deployed before the in-VPC resolver existed; redeploy it).
- Private network: the reconciler approves a connector's advertised route only when it is private **and** inside the `routes` config declares for that connector's own VPC (`connectorVpcs`). Until now any private range was approved, so a connector in one account could advertise another account's subnet in the same site and receive its traffic. A refused route is logged and the rest are still approved (one bad route used to hold back all of them, silently); a route approved earlier that falls outside the declaration is logged, not removed. The rule is per site: once a site lists any connector VPC, every connector in that site must be listed, and one that matches no entry gets nothing approved; a site with no `connectorVpcs` at all keeps the private-range rule. Needs a `NetworkStack` deploy; **before it, check each connector advertises what `connectorVpcs.<account>.routes` says**, or a restarted connector's routes will wait unapproved.
- Private network: a site's access rules are sent compact (about 40,000 user-resource pairs fit under the control server's 4 MB limit, up from about 24,000), the reconciler warns at three quarters of the limit and fails the pass with a clear error above it.
- **Plugin pages: the plugin now owns the whole page.** The portal no longer draws a header (title, version, account picker) above the frame, and the frame fills the page area beside the sidebar; it was stuck at a 20rem minimum. A plugin draws its own title, and its own account picker if it needs one. **The portal no longer tracks a selected account at all** (plugin message protocol 2, plugin packages 0.2.0): it hands the frame the accounts the caller may use and their permissions, and which one the plugin works in is the plugin's own state. For plugin authors: `context.selectedAccount()`, `context.selectAccount()` and the `contextChanged` event are gone; `context.permissions()` is `context.permissionsFor(accountNumber)` and `context.hasPermission(p)` is `context.hasPermission(p, accountNumber)`; `accessChanged` is the one account event; `?account=` links are no longer read. **Every plugin must be rebuilt against the 0.2.0 plugin packages**; a page built on 0.1.x shows "built for a different version of the portal". The reference plugin shows the new shape. Switching between two entries of one plugin (`index.html#/user`, `#/admin`) and the "Try again" / "Reload it" buttons now really reload the frame.
- Private network, opt-in: `network.mirrorImages` (hub) and the `mirrorImages` prop on `ConnectorStack` / `TailnetConnector` run the control servers and connectors from a copy of their image in the account's own registry, made at deploy, so a task restart no longer depends on GitHub's registry being reachable. Off by default; turning it on restarts each control server and connector once, and needs `npm install cdk-ecr-deployment` in the deployment project (an optional peer: nothing extra is installed otherwise).
- Web app: a tab left open across more than one deploy could stop responding to a click on a page it had already recovered once; the click did nothing until a manual refresh. The one-reload-per-page guard from 0.1.18 was never cleared; it now clears on the next successful navigation.
- Web app: the side panel (a resource's or user's details) now shrinks to the room the window leaves the page, down to its own minimum. A width dragged wide on a large screen carried over unshrunk, and on the admin Network page, whose table needs 860px, the panel went off the right edge.
- Web app: being connected to a network where nothing is granted to you now says so. The network's bar chip and the sidebar pill turn amber with "nothing granted", and the empty state explains that every address is blocked and staying connected changes nothing. The connection itself is untouched; a new grant flips it back on the next sync.
- Config: `branding.logoFile` takes a local image file (`.svg`, `.png`, `.jpg`, `.webp`, `.gif`, up to about 47 KB) and embeds it in the web app's config at synth, so a logo no longer needs a public URL. Not together with `logoUrl`.
- Every Lambda function the package deploys carries a description saying what it is for.
- `NetworkStack` no longer prints `CfnResource#addDependency is deprecated` on every synth and deploy.
- Versioning from this release on: bug fixes raise the patch number, a new feature raises the minor, a breaking change raises the major.
- Releases: the four plugin packages (`@fntio/infra-client-plugin-sdk`, `-cdk`, `-ui`, `-example`) are attached to every GitHub Release beside the core tarball, so a plugin author downloads them instead of cloning the repository and running `npm run pack:plugins`. The v0.1.18 Release carries them too (uploaded after the fact, built from the same source). The example README's install step and the Releasing wiki page describe the new path.
- **Upgrade order: deploy 0.1.18 first.** DataStack no longer creates the access-model-v1 `Grants` and `ResourceGrants` tables (unread since 2026-08-17) or exports their names and ARNs. A deployment whose CredsStack or NetworkStack still imports those exports (every version before 0.1.18) fails this DataStack deploy with "export in use", so upgrade through 0.1.18 and deploy its `NetworkStack` by hand before this version. Deployments with `prod: true` keep both tables as orphans (RETAIN): delete them in the DynamoDB console afterwards, turning off deletion protection first; non-prod deployments lose them with the deploy. The one-off v1→v2 migration script is gone with them.

## 0.1.18 — 2026-10-01

- Access correctness: approving a yearly review now renews the standing grant in place and refuses (409) when that grant was revoked after the review was raised — it used to write a fresh grant, so a revoked role came back through the review queue; revoking a grant directly now closes the open review for it, a duration on a review approval is refused (it never applied), and a denial whose revoke fails no longer leaves a DENIED row beside live access. Vending a grant whose role is no longer in the catalog is DENIED with reason `NO_ROLE` instead of assuming a conventional ARN.
- Admin API hardening: every `:userId` must be a Cognito sub or service-user client id (an email used to slip past the last-admin and self-delete guards); `admin` must be a boolean; account and role free-text fields must be strings with length caps (a stored number in an account name broke every accounts list); the user profile-name override follows the same charset rule as admin-set names.
- Catalog deletes: role, account and resource deletes revoke grants, drop group bundles and deny the target's open requests and reviews BEFORE the catalog row goes, and can be repeated after a failure (an already-removed role still sweeps its leftovers before the 404); a cascade no longer leaves an empty group. `DELETE /admin/accounts/{id}` answers 409 while the account still has network resources.
- Offboarding: deleting or demoting a user ends their sessions at once (`AdminUserGlobalSignOut`), and admin routes re-check the admins group once a minute per API container, so an already-issued token cannot keep admin access for the rest of its hour. The API role gains `cognito-idp:AdminGetUser` and `cognito-idp:AdminUserGlobalSignOut` (rides the hub deploy).
- Deploys: the site's hashed assets upload with a one-year immutable cache and `index.html`/`config.json` with `no-cache` (browsers no longer keep the previous shell for a day after a deploy); the web app reloads when a page's chunk from a pruned build fails to load; the deploy workflow verifies the live bundle matches the build. The cdk-nag gate runs in CI (it had been skipping itself when the frontend was not built).
- Security headers: app pages send an enforced Content-Security-Policy (self, the region's Cognito API and the hosted-UI domain; it ran report-only on the development deployment first with no violation across the e2e suite); plugin assets get their own enforced policy that allows the portal only. The shell's boot-failure script is allowed by a hash WebStack computes from the index.html it deploys, and the frontend build no longer inlines critical CSS (its stylesheet link carried an inline `onload`). A plugin that loads anything from a third-party host has never worked under the plugin policy and does not work under the app policy either. The scripts Cognito client (`/.well-known/infra-client`) no longer reveals whether an email address has an account.
- Web app: the admin role, resource and group panels reload their lists when the panel is pointed at another row (they showed the previous row's holders); the Get-credentials dialog is re-created when a toast or deep link switches its role; a sign-out that raced the hourly token renewal no longer signs the user back in; a plugin page keeps its session across a transient renewal failure; the sign-up link works seconds after creating a user (consistent lookup); a refused last-admin delete no longer ends that admin's dev shares first.
- Desktop (needs the next desktop build): the credentials writer never replaces or deletes a profile it did not write (a role renamed to `default` used to overwrite the user's long-lived keys), a settings file that is not a list no longer blocks startup, the device key can no longer appear in a CLI error detail, Electron 44 with fuses set. `cd desktop && npm test` runs the new unit tests.
- API runtime: the handler runs at 1024 MB; the console federation call and the STS/KMS clients have a 4 s deadline so a hang cannot skip the vend's audit row; the vend reads access strongly consistent; the legacy Grants/ResourceGrants tables (access model v1, unread since 2026-08-17) are no longer referenced by CredsStack or NetworkStack at all (no env, no IAM, no output). DataStack still deploys them and keeps exporting their names and ARNs, because CloudFormation refuses to drop an export while a deployed stack imports it and DataStack deploys first. **The next release removes the tables, so deploy this version before upgrading past it** (a manual `NetworkStack` deploy counts). Deployments with `prod: true` keep the tables as orphans (RETAIN); delete them by hand afterwards (turn off deletion protection first).
- Desktop tray: the credential expiry alarms no longer fire all at once when the Mac wakes from sleep. An alarm that comes due while the machine is asleep waits 30 seconds after the wake, so the app can renew the credentials or, past the 12-hour sign-in limit, log out and purge them first; only credentials still on file and still expired are then reported, and "expires in 1 minute" is never said of something already expired. Needs the next desktop build.
